I recommend the normalized approach by creating a separate `regions` table with a region code, display name, and parent region, then adding a `region_id` foreign key to the listeners table. Since the `plays` table receives a new row for every listening event, storing region information in every play would increase write overhead and make the table larger. With normalization, region information is stored once per region, although the report will require joins between listeners, regions, plays, and songs. Indexes on `listeners.region_id` and the relevant join columns can help reduce join costs, but they also require additional storage. Report A taught me that choosing the right composite index, such as `(user_id, played_at)`, can significantly improve query performance without duplicating data across millions of play records. Overall, normalization provides better data consistency and a more manageable schema as the number of plays grows.
